# 09 · 日常运维:备份、重启、出事怎么办

> 这台服务器**没有人坐在旁边守着**。它靠四个 `mc-*` systemd 定时器自己过日子,
> 而维护它的助手(我)的会话记忆会被压缩 —— 今天查清的事,下次可能就没了。
>
> 所以这一篇不是"运维手册",而是三件事:
> **一天里它自己会做什么**、**这些事失败时长什么样**、**出事了先看哪儿**。
>
> 素材来源:`systemctl list-timers` 的**两次快照**(2026-09-17 19:38 / 20:14 JST)、
> `plugins/BlueMap/core.conf`、`plugins/McAI/config.yml` 的文件头、
> `/opt/minecraft` 下的几个 `.bak-*` 文件名。运维经验那几条来自交接记录和
> 本目录的 [`CHANGELOG.md`](CHANGELOG.md),**不是**这次抓素材时验的 —— 逐条标在文末。
>
> 这篇最重要的一句话不是时间表,是那条用三天备份换来的:
> **"我们有备份"在没人看见它成功之前,只是一个假设。**

## 一、一天里它自己会做的四件事

`systemctl list-timers` 的原文(2026-09-17 20:14 JST 那次,一字没改):

```
Thu 2026-09-17 20:14:12 JST       1s Thu 2026-09-17 20:13:12 JST      58s ago mc-status.timer           mc-status.service
Fri 2026-09-18 00:00:00 JST 3h 45min Thu 2026-09-17 00:00:13 JST      20h ago dpkg-db-backup.timer      dpkg-db-backup.service
Fri 2026-09-18 04:00:00 JST       7h Thu 2026-09-17 04:00:01 JST      16h ago mc-backup.timer           mc-backup.service
Fri 2026-09-18 05:00:00 JST       8h Thu 2026-09-17 05:00:01 JST      15h ago mc-restart.timer          mc-restart.service
Fri 2026-09-18 05:10:00 JST       8h Thu 2026-09-17 05:10:08 JST      15h ago mc-chunky-resume.timer    mc-chunky-resume.service
```

整理成人话:

| 时间(JST) | 定时器 | 做什么 | 证据 |
|---|---|---|---|
| **每分钟** | `mc-status.timer` | 采一次服务器状态 | 两次快照:上次 19:37:41 / 下次 19:38:41,上次 20:13:12 / 下次 20:14:12 —— 间隔都是 **60 秒** |
| **04:00** | `mc-backup.timer` | 备份 | 上次 `04:00:01`,下次 `04:00:00` |
| **05:00** | `mc-restart.timer` | 重启 Minecraft 服务端 | 上次 `05:00:01`,下次 `05:00:00` |
| **05:10** | `mc-chunky-resume.timer` | 续跑地形预生成(Chunky) | 上次 `05:10:08`,下次 `05:10:00` |
| (00:00) | `dpkg-db-backup.timer` | **Debian 自带的**,备份的是系统包数据库,和 Minecraft 无关 | 名字和它的 service 都不带 `mc-` |

两个从原文里能直接读出来的细节,别忽略:

- **三个 `mc-*` 的"下一次"都落在整分整秒上**(`04:00:00` / `05:00:00` / `05:10:00`),
  而"上一次"分别晚了 1 秒、1 秒、8 秒。这说明它们是**按日历时间**触发的
  (`OnCalendar`),那几秒是启动开销,不是漂移。
- **`mc-status` 不一样**:它的"下一次"是 `20:14:12`,不是 `20:14:00`。
  两次快照都比整分钟偏了十几秒,而且偏的量不同 —— 看起来是**相对上一次跑完**再等 1 分钟
  (`OnUnitActiveSec` 那一类),所以它的时间点会慢慢往后爬。
  这对"每分钟采个状态"无所谓,但**如果哪天要拿它的采样去算一小时的平均值,别假设它是整分钟对齐的。**

**为什么排成 04:00 → 05:00 → 05:10?**(以下是我的推断,素材里没有写理由的地方)

1. **05:00 是这台服务器一天里最安全的时刻** —— 玩的是一群中学生,那个点没人在线。
   重启会把所有人踢下线,放白天做就是事故。
2. **备份排在重启前一小时**,所以"最新的那份备份"永远是**重启之前**的状态。
   重启是一天里最危险的动作(改过的配置、换过的 jar 都在这一刻第一次真正生效),
   而"出事前的最后一份备份"正好在手上。反过来排(先重启再备份)就会把坏状态备进去。
3. **05:10 比 05:00 晚 10 分钟**,是给服务端启动留的缓冲 —— 地形预生成要连上已经起来的服务端才能续跑。
   10 分钟是怎么定的,素材里没有依据。

> **一天四件事里,只有一件失败时会被人发现(重启:孩子进不来)。**
> 另外三件失败时都是安静的 —— 这就是下面三节的全部内容。

## 二、备份:曾经连续三天,"有备份"是假的

### 事故

备份脚本用 `tar` 打包正在运行的服务器目录。`tar` 有三个退出码:

| 退出码 | 含义 |
|---|---|
| `0` | 全部正常 |
| **`1`** | **有文件在读的过程中被改了 / 有差异** —— 打包出来了,只是不完美 |
| `2` | 真的失败了(致命错误) |

而 `plugins/` 是一个**热目录** —— 服务器正在跑,插件随时在写自己的数据。
于是 `tar` 每次都返回 `rc=1`。脚本写的是"非 0 就算失败",直接退出,**不上传**。

**连续三天没有新备份,而这三天里一切看起来都正常。**

### 为什么没人发现

这是最要命的部分:**看 `systemctl list-timers` 完全看不出来。**

上面第一节那份原文,能告诉你 `mc-backup` "昨天 04:00:01 跑过了"。
它**不告诉你跑成功了没有**。那三天里,这张表长得和今天一模一样。

### 修法和教训

修法很小:**容忍 `rc=1`**(热备份下 `rc=1` 是常态,`rc=2` 才是故障)。

> **教训:定时任务失败要有人看见,否则"有备份"是个假设,不是事实。**
>
> "跑过了"和"成功了"是两件事,而绝大多数监控看板显示的是前者。
> 一个每天准点触发、每天准点失败的定时器,在任何"上次运行时间"类的界面里都是绿的。

### 所以要检查的是这三样,不是定时器

| 想确认什么 | 该看哪儿 | 别看哪儿 |
|---|---|---|
| 备份**成功**了吗 | `systemctl status mc-backup` / `journalctl -u mc-backup` 里那一次的**退出码** | `list-timers` 的"上次运行" |
| 备份**真的落地**了吗 | 目标位置**最新一份文件的时间戳和大小** | 脚本自己的日志说"完成" |
| **能恢复**吗 | 真的解开一份来看看 | 文件存在 ≠ 文件完整 |

**最后一条尤其别跳过** —— `rc=1` 那个故事说明打包这一步本身就允许"不完美"。
我没有在素材里看到任何一次恢复演练的记录。

## 三、重启:每天 05:00,机器人会刷一串错,那是正常的

`mc-restart.timer` 05:00 重启服务端。连带的现象:

- **AI 玩家小麦(mineflayer 机器人)会刷一串连接错误(`ECONNREFUSED`)。**
  这是服务端还没起来时它在重试,**不是 bug**,约 **47 秒**自己接上。
  **不要在这个时候去重启机器人或改它的代码** —— 你会把一次正常的自愈当成故障去"修"。
- **跨重启活不下来的东西,必须自己有一个 unit。** 这就是 `mc-chunky-resume.timer` 存在的原因:
  地形预生成是分批跑的,重启会打断它,所以 05:10 有一个专门的任务把它接回去。

**顺带一条我推断出来的**(素材里没写,但从时间表能推):

> 如果你晚上改了某个配置文件却**没有 reload**,那它会在**第二天 05:00 自己生效** ——
> 在没有任何人看着的时候。要么当场 reload 并验证,要么别在晚上改。

## 四、改配置的三条硬规矩

### 规矩 1:不要用 `sed -i` 或 `mv` 去改一个"某个服务要写的"文件

如果一个文件在某个 systemd 服务的 `ReadWritePaths` 里(白名单里给它开写权限的那种),
那么**换掉这个文件的 inode,就等于把那个服务的写权限弄丢了**:

```
sed -i / mv 的实质 = 写一个新文件,再改名盖上去 → inode 变了
systemd 的写白名单是在服务启动时绑定的 → 它盯着的还是老 inode
结果:那个服务此后往这个路径写,会撞到"只读文件系统"
```

**症状极难认**:服务活着、日志也不一定报错,只是**后台页面上一保存就不生效**。
而且它和你刚做的编辑动作看起来毫无关系。

```bash
# ❌ 会换 inode
sudo sed -i 's/foo/bar/' /opt/minecraft/plugins/X/config.yml
sudo mv config.yml.new /opt/minecraft/plugins/X/config.yml

# ✅ 原地覆写,inode 不变
sudo cp /opt/minecraft/plugins/X/config.yml \
        /opt/minecraft/plugins/X/config.yml.bak-20260917-2015   # 先备份(新建别的文件没事)
sudo cp /tmp/config.yml.new /opt/minecraft/plugins/X/config.yml # cp 是截断写,不换 inode
```

**已经踩了怎么办**:`sudo systemctl restart <那个服务>` —— 重启时会重新绑定当前的 inode。

### 规矩 2:有些配置文件是后台生成的,手改一定会被抹掉

`plugins/McAI/config.yml` 的第一行就是这么写的(原文):

```yaml
# 这个文件由后台「AI 村民」页面自动生成,手改会在下次保存时被覆盖。
# 生成时间: 2026-09-17T00:21:12+09:00
```

这类文件的**真身在生成它的那一侧**。在文件上改,下一次有人在后台点"保存"就全没了 ——
而且不会有任何报错,只是你的改动消失了。

所以:**给这类插件加一个新配置项,必须连生成它的那一侧一起改**,
否则新项在下一次保存时被抹掉,表现出来就是"我明明配了,它就是不生效"。

### 规矩 3:备份文件名带"干什么"和"什么时候"

服务器上现成的两种写法(素材原文):

```
castle1_mobs.txt.bak-hp1784729341                      ← /opt/minecraft 下抓到的
resworld.yml.bak-paid-20260917-192730                   ← CHANGELOG.md 里的
roles.json.bak-sleep-20260917-123914                    ← 同上
```

约定是 **`<原名>.bak-<为了什么改>-<时间戳>`**。
(第一个那串 `1784729341` 看着像 unix 时间戳,但没核实。)

**为什么值得较真**:半年后同一个目录里会有五个 `.bak`,
而"回滚"这个动作发生在出事的时候 —— 那时候没人想现场推理哪份是哪份。
[`CHANGELOG.md`](CHANGELOG.md) 里每条改动都配一行回滚命令,靠的就是这个命名。

## 五、版本别乱升:EssentialsX 锁在 2.21.0

**不要升到 2.22.0+ —— 那之后放弃了 1.21.4 支持。** 这台服务端锁在 1.21.4(见
[`06-platforms-and-login.md`](06-platforms-and-login.md)),所以插件的"最新版"经常不是"能用的版本"。

**为什么这条比听起来更重**:EssentialsX 不是一个边角插件,孩子手上那本玩法书里
大半条命令都是它的,而且好几套玩法是搭在它上面的:

| 素材里的东西 | 落在 EssentialsX 上的部分 |
|---|---|
| 书里的 `/sethome /home /spawn /tpa /pay` | 家、传送、转账全在它 |
| 商店的"出售手中" | `/sell` + `plugins/Essentials/worth.yml` 定价 |
| 每日奖励发钱 | LushRewards 执行的是 `eco give %player% 50` —— 经济账也是它 |

**也就是说这个版本号一升错,孩子那本书上的东西会一起失灵**,而不是某一个功能坏掉。

反过来的坑也有,方向正好相反:`CHANGELOG.md` 里那条"AI 玩家换到 Node 22",
是因为 mineflayer 从 4.26.0 起要求 `node >= 22`,而系统自带的是 20 —— **太旧**同样会咬人。

> **在一台锁死了服务端版本的服务器上,"升级"和"不升级"都不是默认安全的动作。**
> 唯一安全的做法是:改之前先查那个插件自己声明支持哪些 Minecraft 版本,
> 改完在 `CHANGELOG.md` 里留下版本号和回滚路径。

## 六、后台任务会和玩家抢 CPU,而 TPS 不会告诉你

素材里有两个数,放一起看才有意思:

| 数字 | 出处 |
|---|---|
| `render-thread-count: 2` | `plugins/BlueMap/core.conf` |
| 地图配置文件数 **55** | BlueMap 配置目录(≈ 52 个世界都上了网页地图) |
| 05:10 还有一个地形预生成的续跑任务 | 第一节的定时器表 |

也就是说:**这台机器上有两个长期在后台啃 CPU 的活儿** —— 网页地图渲染,和地形预生成。
它们都不是玩家触发的,失败或者跑太猛也都不会有人报告。

[`CHANGELOG.md`](CHANGELOG.md) 里记着(标了未逐条复核):`render-thread-count` 调到 6 会吃掉
16 核里的 11 核,孩子卡在「加载地形中」,而 **TPS 仍然显示 20.0**。

> **这条最值钱的地方不是那个数字,是那个症状:**
> 服务端的 TPS 衡量的是"服务端自己有没有跟上",不是"玩家能不能玩"。
> 后台任务把核吃光时,服务端**确实**很健康 —— 卡的是给玩家发区块的那条路。
> 所以 **TPS 20.0 不能用来反驳"孩子说卡"。**

这也解释了为什么预生成要放 05:10:那个点没人在线,抢 CPU 抢不到人。

## 七、出了这些事该看哪儿

| 症状 | 先看哪儿 | 千万别做 |
|---|---|---|
| 孩子说"进不去",时间在 **05:00 前后** | 就是每天的定时重启,等它起来 | 别急着改 `server.properties` |
| 孩子说"进不去",不在 05:00 附近 | 版本翻译那一层([`06`](06-platforms-and-login.md)):客户端自动升级了?基岩版端口填错了? | 别先怀疑服务端,它锁着版本没动 |
| 孩子说"卡在加载地形中",**但 TPS 显示 20.0** | 后台占核:BlueMap `render-thread-count`、预生成任务 | **别拿 TPS 当证据说"不卡"** |
| 想确认"有备份" | 目标位置最新文件的**时间戳**,加 `journalctl -u mc-backup` 的**退出码** | 别把"定时器触发了"当成"备份成功了" |
| 机器人 05:00 附近刷 `ECONNREFUSED` | 什么都不用做,约 **47 秒**自愈 | 别在这时候重启机器人或改代码 |
| 后台改的配置"过一会儿又没了" | 那个文件头上是不是写着"由后台页面自动生成" | 别再手改文件,去改生成它的那一侧 |
| 某个服务突然写不进自己的配置 / 后台保存不生效 | 刚才是不是用 `sed -i` 或 `mv` 动过那个文件(inode 换了) | 先 `systemctl restart <那个服务>`;以后别用 `sed -i` |
| `/home` `/pay` `/sell` 一起失灵 | EssentialsX 版本被升过没有(必须 **2.21.0**) | 别"顺手升到最新" |
| 菜单里某个按钮**整个消失** | 同一格子多个 item 少写了 `priority` —— [`CHANGELOG.md`](CHANGELOG.md) 2026-09-17 用一次 20 分钟线上故障换来的 | 别先当成权限问题查 |
| 改完插件不确定线上跑的是哪一版 | [`CHANGELOG.md`](CHANGELOG.md):每条都带文件路径和回滚命令 | 别靠记忆 |

## 八、总结

这台服务器的"运维"其实只有一条主线:

> **它每天自动做四件事,其中三件失败时是安静的。**
>
> 备份失败 = 没有新文件,界面还是绿的;
> 预生成断掉 = 地图少一块,没人会报告;
> 状态采集停了 = 你只是看不到东西了。
> 只有重启失败会立刻有人喊 —— 因为那一条的"监控"是**一群等着上线的孩子**。
>
> 所以真正的运维工作不是"做这四件事",是**给另外三件装上"失败时有人看见"的那根线**。
> 到写这篇为止,这根线**还没有装完**(见下面第 9 条)。
