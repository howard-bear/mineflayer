# 同一个名字,不同的圆心

> Owner 批准了麦豆(第三个 AI 玩家,设定是小麦的儿子)学干活:收麦子、种回去、砍树、存箱子。
> 这四样线上都有人在做,麦娘收麦子、种地、存箱子,小麦砍树,而且都跑得好好的。
> 我照抄了四条,只把安全门槛换成麦豆的,引擎自检全过:
> 判据都注册过,动作代码都有,格式能加载,id 不重复。
>
> 派 4 个人对着线上代码只读核,再加 1 个人专门反驳他们。结论是:**4 条今天一条都不能上。**

## 一行

```js
'熟了的庄稼': () => farmScan().ripe        // bot.real.js:3905

function farmScan() {                        // :3728
  if (!homePos) { out.why = '还没有家,不知道该在哪儿种地'; ... }
  const c = homePos.floored()                // ← 圆心是【谁】的家?
  for (let dx = -FARM_R; dx <= FARM_R; dx++) // FARM_R = 6
```

判据名叫「熟了的庄稼」,麦娘用和麦豆用,**写出来一模一样**。
可它有一个看不见的参数:`homePos`,也就是**这个角色自己的家**。

```
麦娘的家  = 麦田就在门口       → 扫的是麦田
麦豆的家  = 小麦的旧泥土房     → 扫的是泥土房周围 13×13
两个家相距约 16 格,两个 13×13 的框一格都不重叠
```

所以「帮妈妈收麦子」**碰不到妈妈的田**。它扫的那块框里有:

- 麦娘前一天在旧家开过、后来扔下的田。反驳者推断当时约有 4 格长着麦子;Java 版里,种着作物的耕地不会退回泥土
- 孩子们的建筑区

能挡住它的只有一道护栏,**旁边 3 格内有没有人造方块**。而耕地、小麦、水、泥土都不算人造方块。
孩子开的一块没圈地的麦田,只要离木板、栅栏、火把超过 3 格,麦豆就会去收,「补种」那条还会替人家种回去。
**这就碰了「不拿别人东西」的红线。**

## 这和第 25 篇是一对

[第 25 篇](25-one-codebase-two-identities.md)里,「有没有人在叫我」**本该按角色区分,却写死成了一份**,于是麦娘拿着小麦的名字认领消息。

这一篇正好反过来:「麦田在哪」**本该全家只有一份,却是按角色各算各的**。

两次的根子是同一个问题:
**一个判据依赖的某个状态,到底是「这个角色的」,还是「全家的」?**
名字不会告诉你。在第一个角色身上永远是对的,所以你测第一个角色永远测不出来。

就算把圆心改对了也不够。反驳者补了两条:

- 代码里没有「收割锁」,麦豆和麦娘会同时去收同一块田
- 麦豆不会把收成存进粮箱。小麦不是食物,背包不紧的时候一粒都不存,会一直揣在他身上。
  麦娘做面包要自己背包里至少有 3 个小麦,结果「帮妈妈」反而让妈妈缺了原料

## 第二层:放行一个动作,放行的不只是这一条脚本

砍树那条的门槛我写得很严:血量 ≥ 16、白天、离家 ≤ 40 格。
但 `gather_wood` 成功一次,会顺手做一件事:

```js
if (gained > 0) { places.remember('tree', bot.entity.position, ...) }   // :1680-1682
```

麦豆从此**记得一片林子**。这会叫醒两样原来一直睡着的东西:

1. **硬规则 1.12**:身上木头少于 20、附近没树、又记得林子,就每 45 秒强制派它去林子。
   这条规则**不看天黑、不看离家多远**,血量只要大于 10。硬规则排在脚本前面。
2. **麦豆现有的「跟着爸爸去林子看他砍树」**:它的开工条件就是「记得林子」,以前永远不成立。
   现在成立了,去的却是麦豆自己记的那片林子,到了还会顺手砍,从「看」变成了「砍」。

我写的三道门槛,被两条**我根本没写、也没看的路**绕了过去。

## 第三层:门槛只在开工那一刻查

```js
'有能砍的树': () => hasChoppableTree(32)    // 以【当前站的位置】为圆心,不是家
```

「离家 ≤ 40」只在接这件活的那一刻、以及出事(天黑、受伤、背包满)时查。
砍树过程中,每一轮都从当时站的位置往外再找 32 格。
离家 40 格开工,第一棵树就可能在离家约 72 格。目标表要求麦豆离家不超过 64 格。

## 我自己同一天差点犯的同类错

几个小时前,我想把一批「判据、动作都齐了,只差一道安全门槛」的新脚本,照抄同类老脚本的门槛一口气解锁。
逐条看才发现,其中「进资源世界挖圆石」的步骤只有**去入口 → 回家 → 存东西**,一步挖矿都没有。
还有几条挂在 Owner 还没拍板的搬家上。

**「字段都齐了」不等于「行为是对的」。**这和本篇是同一件事,只是换了个样子。

## 核查怎么做的,以及反驳者值多少

| 视角 | 查什么 |
|---|---|
| 判据语义 | 每个判据在**麦豆身上**算的是什么:圆心在哪、半径多大、数哪些东西 |
| 动作行为 | 每个动作在麦豆身上**实际**走到哪、挖什么、开哪口箱子、失败了怎样 |
| 安全红线 | 会不会碰别人的东西、走太远、夜里出门、踩坏耕地 |
| 引擎和配合 | 能不能加载;和麦豆现有脚本、硬规则、「遇事才想」怎么排先后 |
| **反驳者** | 对每条严重问题**重新取证、尽量推翻**;再找四个人都没查的角度 |

每条结论都要附 `文件:行号` 加引用的代码,或者日志原文。

四个视角一共报了 31 条严重问题(blocker 或 major)。反驳者原样确认 17 条,部分更正 14 条,**没有一条被整条推翻**。
部分更正的 14 条里,有 9 处是说重了,或者证据站不住。有两条值得记下来:

- 3 个视角都说「箱子满了会死循环,得改代码加判据」。
  反驳者指出,**现成的判据「有箱子」就是 `myChest ? 1 : 0`**,箱子报满被忘掉后自己会变 0,只改表就能止住循环。
- 一个视角说小麦历史上 285 次砍树失败都是「菜单看 24 根原木、执行器只看 12 根」造成的。
  反驳者重数是 277 次,而且最近两次的真实原因是**把被插队的活接回来时,不重查开工条件**,当时附近已经没树了。
  代码不一致是真的,把失败归到它头上的证据站不住。

**没有反驳者,这份报告里会有两条错的结论和一条多余的代码改动。**

## 顺带查出一件正在发生的

Owner 定的是「麦豆遇怪只跑不打」。麦豆的日志:

```

「正在还击 / 还手 / 拿出 X 再打」  259 行
按间隔 > 30 秒拆开                 78 场

```

原因还是同一个形状:角色能做什么,是在**出菜单、执行动作、硬规则**三个出口各挡一次的,
**反射层的「被打就还手」不查角色。**

## 给一个角色照抄脚本之前,查这四样

1. **每个判据的隐含参数**在这个角色身上是什么:谁的家、谁的箱子、以谁为圆心、多大半径。
   同名判据,换个角色可能换了意思。
2. **放行的动作有哪些副作用**:它写了什么记忆、哪些硬规则会读这份记忆。
   `grep` 这个动作的每一处调用,还有那份记忆的每一个读取方。
3. **门槛是只在开工时查,还是全程都查。**只在开工时查的门槛,管不住干活过程中越走越远。
4. **反射层有没有按角色挡。**脚本层挡住了,不等于这个角色就不会做。

> 这四条脚本,麦娘和小麦跑了好几天都没出事。
> **在原来的人身上跑得好,正是它在新的人身上会出错的原因:你根本想不到要去查。**
