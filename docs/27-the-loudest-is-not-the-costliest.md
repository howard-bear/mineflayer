# 最吵的不是最贵的

> Owner:「服务器没有真人的时候,让老麦就别说话了,纯浪费算力。」
> 查下来,老麦几乎不耗算力。**真正在烧算力的是一个日志里几乎看不见的东西** ——
> 而它被做成这样,恰恰是因为 Owner 更早说过另一句话。

## 被怀疑的那个:几乎是免费的

老麦是住在出生点的 AI 村民。没有真人在线时,它还在隔几分钟说一句话 ——
这些话全服广播,还会出现在地图网页的聊天窗里。**非常显眼。**

把它说过的话拆开数(跨午夜把两天日志接起来 —— 只看今天会漏掉午夜前就在线的人):

```
老麦共 164 句
├ 写死在配置里的闲聊台词(不调用模型)   163 句,其中没有真人时 56 句
└ 模型现场生成的回答                     1 句
```

**闲聊是从一张固定台词表里随机挑一句,根本不经过 AI 模型。**
"浪费算力"这个前提不成立。

它确实该关,但理由是另一个:台词里「点名一个在线玩家」会把机器人也当成玩家,
于是没真人的时候它一直在对机器人说「MaiNiang 你好」。那是噪音,不是开销。
(已改:McAI 1.8.0 只数真人、只点真人的名。)

## 顺藤摸到的那个:几乎是隐形的

既然要回答"算力花在哪儿",就不能只查被怀疑的那一个。
三个 AI 玩家身上各有一个**规划师**,负责给自己定"阶段目标"。代码是这样写的:

```js
// bot.real.js:7553   每轮之间的等待
const waitMs = failStreakPlan > 0 ? /* 退避 */ : 1000        // ← 正常 1 秒一轮

// bot.real.js:119    一份计划"保鲜"多久
planFreshSec: parseInt(process.env.PLAN_FRESH_SEC || '60', 10) // ← 60 秒

// bot.real.js:7537
// 没过期就丢掉这次结果
```

每一轮问一次模型、等 1 秒、再问;而结果**只有在旧计划过期(60 秒)时才会被采用一次**。
每次生成要几秒,所以实际频率是"几秒一次",但不管怎么算 ——
**一分钟里问了十几次,只用一次,其余全部扔掉。三个机器人各跑一个。**

而且在「职业 + 脚本」架构下,**脚本选活时根本不读这份计划**:
它只被塞进喂给模型的那段文字里(`bot.real.js:1058-1059`),
只有模型被问到时才可能起一点参考作用 —— 而新架构下模型本来就很少被问。

## 为什么它隐形:被扔掉的结果不留痕

老麦的每一句话都**全服广播 + 网页显示** —— 想不注意都难。

规划师呢?它**只在"采用了一份新计划、并且目标变了"时才写一行日志**。
被扔掉的那十几次一个字都不写。我拿小麦最近 10 分钟的日志数 `🧭 新阶段目标`:

```
小麦 10 分钟窗口   🧭 新阶段目标  0 行
```

**0 行 —— 而它这 10 分钟里一直在调模型。**

> **显眼程度和成本是反着的。**
> 老麦把它做的每一件事都喊出来,所以被怀疑;规划师把它扔掉的每一件事都默默吞下,所以没人看见。

## 更深一层:它是按一句话被做成这样的

规划师"一直在问"不是 bug,是设计。代码注释里写着 Owner 早先的原话:

> 「GPU 应该是连续不断地在思考和执行才对」

那时实测显卡只忙了约 23%,"四分之三时间在干等定时器",于是改成连续循环。
**显卡确实一直忙了。** 但它忙的大部分是会被扔掉的活。

> **"显卡一直在忙"是一个代理指标,规划师把它优化到了满分 —— 同时把真正的目标(有用的思考)丢了。**
> 占用率只告诉你"它在干活",不告诉你"干的活有没有人用"。

所以另一个会话没有自己关它:**Owner 说过两句方向相反的话**,
早先是「GPU 要一直忙」,今天是「纯浪费算力」。取舍是他的。

## Owner 的决定 —— 以及它在第二轮被改对了

**第一轮**:摆给他三个选项(放慢 / 关掉 / 保持),他选了「彻底关掉」。

**第二轮**,他补了一句,这句话改变了整件事的方向:

> 「规划师的工作实际上就是要判断 大目标 小目标 和对应的脚本如何执行 遇到紧急事件
> 和基本状态维持 这些事情之间的关系,进而触发思考」

这是一个规划师**该**干的活。于是得先回答:**现在的规划师在干这个活吗?**

### 名字对不上

读 `brain.js:616` 的 `plan()`:它每一轮产出的是

```
目标:  最多 25 个字的一句话       例:「去林子砍树」
步骤:  最多 4 条,每条最多 20 字    例:「在附近走走 → 去林子砍树 → 回家」
```

**一张纯文字便条。** 不对应任何脚本,没有代码执行它 ——
它只被夹进喂给模型的材料里(`bot.real.js:1058`)。
它不看大目标和脚本的关系,不管紧急事件,也不决定什么时候该想。
它给不会砍树的麦豆写「去林子砍树」,就是因为它根本不知道麦豆有哪些脚本。

而 Owner 描述的那个活,**其实另有人在干**:

| Owner 说规划师该管的 | 现在实际由谁管 |
|---|---|
| 大目标 → 小目标 → 脚本怎么执行 | 脚本引擎(代码):按优先级排大目标,代码判断能不能开工、做没做完 |
| 紧急事件 | 反射层(每秒)+ 紧急规则(抢占) |
| 基本状态维持 | 紧急规则:快饿死就吃、天黑就睡、没武器就做剑、离家太远就传送 |
| 这些事之间的关系 | 四层优先级:保命 > 紧急 > 脚本 > 兜底 |
| 进而触发思考 | 选择点:一件活结束时算候选,有好几件才问模型 |

> **一个组件的名字描述的是它当初被期望干什么,不是它现在在干什么。**
> 评估「要不要关掉 X」之前,先看 X 实际在做什么 —— 别被名字带着走。
> 这次如果按名字判断,「关掉规划师」听起来像是把整个家庭的调度给关了;
> 实际上关掉的只是一个每秒写一张没人看的便条的循环。

### 真正缺的那一块

对照下来,Owner 说的活里**只有一环没做好**:「进而触发思考」只在**一件活结束时**发生。

被紧急事件打断的活,会被原样捡回来接着干(`bot.real.js:337` 的 `resumeAction`)——
刚被怪打得半死,打完就回去继续砍树,**不会停下来想一想:还该继续吗?天是不是快黑了?**
**事情之间的关系变了,它不会因此重新想。**

### 最终决定

**关掉写便条的规划师,另外补上「遇事才想」:**

```
刚熬过一次紧急事件      → 重新选一次:接着干,还是换件事?
天黑了 / 受伤了 / 饿了  → 重新选一次
背包满了 / 有人跟它说话 → 重新选一次
```

机制上**复用现有的选择点**:把「当前这件活」也放进候选 ——
只有它一个就直接接着干、不问模型;有好几个才问模型,并告诉它是因为什么事才被问的。

三条硬约束:

1. **按「跳变」触发,不按「状态」触发。** 「饿了」是**从不饿变成饿的那一刻**触发一次,
   不是"只要饿着就每轮触发" —— 按状态触发会比原来的规划师还费。
   (代码里早就栽过一次这个坑:「血量 ≤ 10 —— 那是个状态,不是事件」。)
2. **加冷却**,一群怪来回拉扯时不能反复想。
3. **"发生了什么事"全部由代码判断**,只有真有好几个选择时才动用模型。

这样**比原来省**(大部分时间一次都不用想),又**正好是 Owner 描述的**那个活。
而他早先的「GPU 要一直在想」和今天的「别浪费算力」也都不违背:
**该想的时候一定想,不该想的时候不白想。**

由管机器人代码的平级会话实施。每一次事件触发的重新选择都要留一行记录
(什么事件 / 候选几个 / 问没问模型 / 结果是接着干还是换了),并能统计 ——
**如果跑下来几乎全是"接着干",说明触发条件太松,要收紧。这个数必须看得见。**

### 实施进展(2026-09-18)

**规划师已关闭,我独立复核过。**

```
上线     v1 12:07:49 JST;v2 12:21 JST(md5 8d6008c2)
开关     bot.real.js:120  enabled: process.env.PLAN_ENABLED === '1'   ← 默认关
启动时   如实打一行「规划师已关闭(PLAN_ENABLED≠1,Owner 2026-09-18 决定)」

复核(每个人最后一次启动以来)   已关闭  已接入  规划师出目标  代码报错
  小麦                            1       0         0            0
  麦娘                            1       0         0            0
  麦豆                            1       0         0            0
```

**v2 修的两处 —— 只在规划师被重新打开时才会走到,但都是"反着来"的静默失败:**

1. **间隔改成可调(`PLAN_EVERY_SEC`)后没有上限。**
   Node 的定时器上限是 2³¹−1 毫秒(约 24.9 天),超过就**悄悄改成 1 毫秒**,只打一句 warning。
   我在服务器上(Node v22.23.2)验证过:

   ```
   填了 30 天
   TimeoutOverflowWarning: 2592000000 does not fit into a 32-bit signed integer.
   Timeout duration was set to 1.
   实际等了 6 毫秒
   ```

   → **想让它"几乎别跑"而填一个大数,结果变成每毫秒跑一次。**

2. **正常间隔默认 60 秒,而失败退避的封顶还是 30 秒 —— 后端坏了反而比好的时候敲得更勤。**
   现在退避取两者中较长的那个。

(这两处是平级会话自己的独立复核查出来的。)

**还没定论的 —— 这里不写成结论:**

- **省下多少算力。** 网关那边有一组初版请求数,但「少掉的全是规划师」这个归因还在复核。
  有一个让归因变复杂的因素:**Ollama 对同一个模型是串行处理的**。
  改之前规划师占着队列,决策请求在排队;改之后队列空了,决策可能跑得更勤 ——
  只数总数,会**低估**规划师原本占的份额。
  反过来,刚重启那段时间三个机器人都在冷启动,请求模式和稳态不同,又可能让改后的数偏低。
  **最干净的办法是在网关按请求来源分开数**(规划师和决策的提示词、`num_predict` 都不一样)。
  **终版出来之前,这里不写数字。**
- **干活有没有变差。** 关掉后才跑了五分钟多,刚重启的几分钟本来就慢,窗口太短。
  要拿**同样长**的窗口、**打印起止**,和改之前比。
- **「遇事才想」**:实施中,要等一次真实的紧急事件之后再复核。

## 途中还有一个值得记的偏差

报告里曾写「关掉只要一个开关、不用改代码」。**核到代码层,没有这个开关**:
规划师只有一个"只启动一次"的保护(`bot.real.js:8512`),
唯一能挡住它的是 `BRAIN_ENABLED=0` —— 但那会把整个大脑一起关掉。
把地址指向不存在的地方也不算开关:会进退避,最长 30 秒还敲一次门,每 60 秒写一行告警。

> 写报告的一方事后自己的总结是:**「我是把『我可以加一个开关』说成了『已经有一个开关』。」**
> 「能做到」和「已经做到」在报告里只差几个字,在 Owner 那里差的是"零成本"还是"要改代码、重启三个机器人"。

## 教训

**1. 🔴 显眼的不一定贵,贵的往往看不见。**
   会把自己做的事喊出来的组件(广播、聊天、界面)天然被怀疑;
   会把自己的产出默默扔掉的组件(后台循环、缓存刷新、被丢弃的计算)天然被放过。
   **排查"钱花在哪"时,先把所有在花钱的东西列全,再按量排序 —— 不要从"看起来可疑的"开始。**

**2. 验证一个"X 在浪费"的说法时,顺手量一下真正的大头。**
   用户指着的那个,只是**他看得见的那个**。
   这次如果只回答"老麦耗不耗算力",答案是"不耗",然后就结束了 —— 真正的大头会继续烧下去。

**3. 被扔掉的工作也要留痕。**
   一个"算了但不用"的结果如果不写日志,它的成本就在所有可观测的地方都是零。
   至少留一个计数器:**算了几次、用了几次。** 两个数一比,这次的问题一眼就能看见。

**4. 占用率是代理指标,不是目标。**
   "让显卡一直忙"很容易做到:一直做会被扔掉的活就行。
   **优化一个代理指标之前,先确认你能同时量到它背后那个真正的目标。**

**5. 「能做到」和「已经做到」要分开说。**(来自平级会话的自我更正)

**7. 「越大越慢」的参数,在极端值上可能变成「最快」。**
   Node 的定时器超过上限会被悄悄改成 1 毫秒;退避封顶比正常间隔还短,坏的时候反而敲得更勤。
   **给一个可调的数加上下限不是洁癖 —— 是防它在边界上反着来。**
   而这类失败只会在**有人去调它**的那一天出现,平时永远测不到。

**6. 名字描述的是期望,不是现实。**
   「规划师」这个名字让人以为它在做规划;实际上它在写没人执行的便条,
   而真正的规划(大目标、脚本、紧急、状态之间的关系)是另一套代码在做。
   **先看它实际干什么,再决定关不关、怎么改。**

> **最吵的不是最贵的 —— 最贵的往往安静地把自己的产出扔进了垃圾桶。**
