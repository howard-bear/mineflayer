# 那不是对照组,那是两个不同的时刻

> 同一口箱子:**小麦能开,麦娘一次都开不了。**
> 这个对照看起来干净得不能再干净 —— 排除了箱子坏、排除了太远,直指"是谁"的问题。
> 它生出了三个互相矛盾的解释,**三个都是错的**,其中一个我还专门写了一整篇 docs。
> 真相是:那两次观察隔了 **1 分钟**,而因果事件正好发生在那 1 分钟里。

## 完整时间线(全部换算成 UTC)

```
15:16:xx  小麦「往箱子里存了 19 个木料」                      ← 箱子是好的
15:17:21  🧱 (-18,65,160) 放上 dirt                          ← 小麦盖屋顶,把土盖在了自己箱子正上方
15:28:37  麦娘第一次「打不开箱子(windowOpen 超时)」          ← 11 分钟后
   ...    连续 28 次失败
16:06:59  最后一次失败
16:07:38  [Rcon: Changed the block at -18, 65, 160]           ← 人工清成空气
16:09:44  🔬 开箱子成功,窗口 id=1
   此后    失败 0 次
```

原因是 Minecraft 的一条原版规则:**箱子正上方有实心方块,箱子就打不开。**
机器人给自己的房子盖屋顶时,把土铺到了自己唯一那口箱子头顶上。
更难认的是:那块土后来长成了草方块 —— **从材料上看不出是它自己铺的。**

一个变量、一次去除、前后各一段、0 次反例。这条因果是闭合的。

## 那个"对照组"为什么骗了所有人

```
小麦 15:16 能开  ←┐
                  ├─ 中间隔着 15:17:21 那块土
麦娘 15:28 不能开 ←┘
```

**它不是"同一个世界里的两个个体",是"两个世界里的同一口箱子"。**

而它给出的信号极具误导性:去掉"箱子坏了""距离太远"之后,剩下的差异**看起来**只有身份。
于是三个人分别推出了三个解释:

| 谁 | 解释 | 为什么听起来对 | 为什么是错的 |
|---|---|---|---|
| 平级会话(第一版) | 被掐掉的合成留下没关的窗口 | 机制真实存在,链条完整 | 全日志**只有 1 次**封顶掐掉,发生在 **15:58** —— 比第一次失败晚半小时 |
| **我** | 同上,还写成了 docs | 我把它引用的每一行源码都逐行核过了 | **我核的是"机制存在",不是"机制发生过"** |
| 平级会话(第二版) | GP 领地权限不含开容器 | 有 `/trust` 只写进 `Builders` 的事实 | 箱子在**删领地前 26 分钟**就恢复正常了 |

> **三个解释都能解释现象。这恰恰说明"能解释现象"是个很低的门槛。**

## 我这一篇的第一版是错的,错法值得单独看

我拿到的是一份**证据很足**的机制报告:时间线、逐条排除、五个源码点。
我做了我以为足够的核实 —— **把五个源码点全部对着 mineflayer 4.39.0 实际安装包逐行核过**,
其中还揪出对方一个错(说"库里没有超时",其实 `promise_utils.js:102` 的 `once` 默认 20 秒)。

核完我很有底气。然后写了一整篇。

**而我从头到尾没有验证过最关键的那一步:那个被掐掉的合成,真的发生过吗。**

日志里一查就知道:麦娘整个日志**只被封顶掐掉过 1 次**,15:58,
比第一次开箱失败(15:28)晚了整整半小时 —— **结果不可能早于原因。**
一条 `grep -c 卡了` 就能推翻的事,我在核了 7 处源码之后仍然没做。

> 这正是 [23](23-sent-is-not-received.md) 那条教训隔了一天换个形状又咬我一次。
> 那次是「我验的是我做完了,不是它做到了」;
> **这次是「我验的是机制存在,不是机制发生」。**
> 两次的共同点:**我验的都是我手边那一头。**

## 「清完照样失败」是怎么得出来的:两份日志,两个时区

那块土是被清掉过的,而当时的判断是「清完她照样失败,所以不是唯一原因」。
这个判断把真因从嫌疑名单上划掉了,代价是后面又生出两个错误解释。

它是这么来的:

```
服务器日志(JST):  [01:07:38] Changed the block at -18, 65, 160
机器人日志(UTC):  15:28:37 ~ 16:06:59  连续失败
```

`01:07` 看起来远远早于 `15:28` —— **于是"清了还在失败"。**
换算过来,`01:07:38 JST = 16:07:38 UTC`,**在所有失败之后**。

> **两份日志、两个时区,而你的结论完全建立在先后顺序上 —— 这是最容易出错、也最难自查的一类推理。**
> 排时间线之前先把所有时间戳换算到同一个时区,再排。

## 还有一个查日志时的陷阱:用今天的字符串去搜昨天

复盘时要回答「箱子是什么时候恢复的」。用的办法是 grep 一个成功开箱的日志文案。
得到的答案比真实时间**晚了 75 分钟**。

原因:那个文案是**后来才改成现在这样**的。改动之前的记录用的是旧写法,
于是 grep 把整段改动之前的历史**静默地漏掉了** —— 没有报错,只是少了几行。

> **用现在的字符串去检索历史,会漏掉改动之前的全部记录。**
> 而漏掉的样子和"那段时间没发生过"一模一样。

这和本篇的主题是同一个形状:**一个看起来在回答问题的检索,其实回答的是另一个问题。**
自查办法很简单:**先不加条件数一遍总量**,再加条件数一遍。
两个数差得离谱,就说明你的检索条件本身有时间偏见。

## 教训

**1. 🔴 对照组必须是同一时刻。**
   「A 能、B 不能」只有在**同时**观察时才指向"A 和 B 的差别"。
   隔了时间的两次观察,中间世界可能已经变了 —— 那时它指向的是**变化**,不是**差别**。
   问自己一句:**这两次观察之间,有没有人动过什么?**

**2. 一个能解释全部现象的机制,不等于真因。**
   这次有三个都能解释全部现象。**"讲得通"是最低门槛,不是证据。**
   真正的证据长这样:**一个变量、一次去除、前后各一段、零反例。**

**3. 核实要核到"它发生过",不只是"它可能发生"。**
   我把七处源码逐行核过 —— 那只证明了**这个机制在这个库里是可能的**。
   而"它这次有没有发生",是另一个完全独立的问题,**而且往往一条 grep 就能回答**。
   **先花十秒回答那个,再花一小时读源码。**

**4. 排时间线之前,先统一时区 —— 而且要【写下来】。**
   光"知道有时差"不够:这条规矩本来就写在项目记忆里,知道的人照样错了。
   可执行的版本是:**两个来源的时间戳放在一起比之前,先把其中一个换算出来写在纸面上,再比。**
   (这条的可执行化来自平级会话。)

**4b. 检索历史时,先确认你的关键词在那段历史里存在。**
   文案改过、字段改名、格式升级 —— 都会让今天的 grep 对昨天失明,而且是静默的。

**5. 沉默不是排除证据,除非你专门验过它在这种情况下会说话。**
   (来自平级会话:它用"没收到 GP 的拒绝消息"排除了权限,
   而那条"GP 会说话"的实证来自**拒绝建造**,不是**拒绝开容器**。)

**6. 别人如实标出的「我不知道」,到了转述者笔下不该变成「没有」。**
   (同样来自平级会话:调研员写的是「`promise_utils.js` 不在快照里,读不到」,
   综合的时候变成了「库里没有超时」。**转述时最容易丢失的就是不确定性。**)

**7. 去找新解释之前,先确认旧解释是【被证据排除的】,不是【被我算错排除的】。**
   这次真因一度就在手上 —— 它被动手修过,然后因为**一次时区误读**被划掉,
   于是三个人转头去找新解释。**划掉一个嫌疑人的那一步,和指认一个嫌疑人的那一步,
   应该受同样严格的检验。** 而实际上前者几乎从不被复查。
   (来自平级会话。)

> **「同一个东西,他行我不行」—— 先问这两次是不是同一个时刻,再问是不是同一个人。**

## 附:一个真实存在、但这次没有发生的危险

第一版那个机制虽然不是这次的真因,**但它在 mineflayer 里是真实可能的**,
而且我逐行核过。留在这里当参考,**不要再把它当成任何现象的解释**。

```js
// inventory.js:581   点格子时,目标窗口是【隐式】选的
const window = bot.currentWindow || bot.inventory

// inventory.js:433-440   只有 closeWindow 会把窗口内容同步回背包
function closeWindow (window) {
  bot._client.write('close_window', { windowId: window.id })
  copyInventory(window)          // ← 唯一调用点
  bot.currentWindow = null
  ...
}

// simple_inventory.js:83
async function disrobe (destination) {
  assert.strictEqual(bot.currentWindow, null)   // ← 窗口没关就直接 AssertionError
}
```

如果一个窗口**真的**泄漏了,代价不是"多占点内存":
后续每一次点格子会被悄悄改道打进那个残留窗口(槽号错位,不报错),
`bot.inventory` 会一直停在开窗前的快照,脱装备会抛断言错误。
**泄漏一个全局独占的单例,比泄漏可再生资源贵得多** —— 这条判断仍然成立,
只是这次没轮到它。

还有一个顺带核出来的、**与本次无关但会绊人**的点:

```js
// inventory.js:407
const [window] = await once(bot, 'windowOpen')     // 看着像 events.once
// promise_utils.js:102
function once (emitter, event, timeout = 20000) {  // 其实是自家的,默认 20 秒
```

`Event windowOpen did not fire within timeout of 20000ms` 是**库自己抛的**。
**看到一个眼熟的名字,先确认它是不是你以为的那个。**
