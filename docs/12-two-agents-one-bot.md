# 两个 AI 同时改一个生产机器人

> 这不是假设。**两个 Claude 会话隔 22 秒先后部署了同一个文件。**
> 那次侥幸是合并而不是覆盖,但那是运气 —— 部署脚本当时一把锁都没有。

## 怎么发生的

一个会话从另一个 fork 出来,两边都拿到了同样的上下文、同样的任务、同样的服务器凭据,
于是**各自独立地**发现了同一批 bug、写出了同名的函数、推上了同一台机器。

fork 继承上下文这一点是关键:两边不是"抄"对方,是**平行演化出了几乎一样的代码**。
所以事后连"谁写的"都说不清 —— 也不必说清。唯一要紧的是:**谁最后部署,谁的版本在跑。**

## 原来的部署脚本为什么会互相抹掉

```bash
mv -f _new_bot.js bot.real.js     # 无条件覆盖,不留任何痕迹
```

没有互斥、没有版本校验、没有审计。两个人同时跑:

- 如果只是时间错开 —— 后推的那个**静默覆盖**先推的,先推的那些修复消失,而**日志上看不出来**
- 如果真的同时跑 —— `node --check`、备份、替换、重启会交错,结果不可预测

## 三道锁

**1. `flock` 非阻塞互斥** —— 同一时刻只允许一个部署在跑,第二个当场中止并提示去查是谁占着:

```bash
exec 9>"$HOME/.mcbot-deploy.lock"
flock -n 9 || { echo "另一个部署正在进行,查一下是谁:fuser -v $HOME/.mcbot-deploy.lock"; exit 1; }
```

**2. `EXPECT_MD5` 乐观并发检查** —— 这是最关键的一道:

```bash
EXPECT_MD5=<你读代码时的那个 md5> bash ~/deploy_safe.sh
```

如果线上文件已经被别人换过,就**拒绝而不是覆盖**,并打印实际的 md5 让你去合并。
不传就跳过(向后兼容)。

> 这就是数据库里的乐观锁:**"我是基于 X 改的,如果现在不是 X 了,别让我写。"**

**3. `~/deploy-audit.log`** —— 每次追加「时间 / 用户 / from→to 的 md5」。
撞车之后能查出来到底发生了什么。

## 给做同样事情的人的几条

1. **只要有两个 agent 能碰同一个生产文件,就一定要有乐观并发检查。**
   `flock` 只挡"同时",挡不住"先后" —— 而"先后覆盖"才是真正静默、真正致命的那个。
2. **先约定分工,再动手。** 我们最后的分工是:一个会话管服务器代码,
   另一个管对外文档和汇报。约定写进共享文档,两边都能看到。
3. **不确定就只读。** 发现对方也在推之后,我方停止部署改成只读监控 ——
   代价是几个小时的产出,收益是没有把对方的修复抹掉。
4. **跨会话对账会抓出单边看不见的错误。** 合并结论时,对方查出的东西
   直接推翻了我这边的一个核心结论(而且是已经发布出去的)。
   **如果两边各写各的,那个错误会一直留在公开仓库里。**
5. **归因要留余地。** 对方一度把三次不知情的部署记成"子代理擅自上生产机",
   还据此写了一条记忆;对账之后发现真凶是我。**在多 agent 环境里,
   "谁干的"比"发生了什么"难查得多,而且错的归因会沉淀成错的规则。**
