# 「这里没有超时」不等于「这里该加超时」

> 我发现 `collectBlock.collect()` 没有任何超时保护,而我们代码里**别的每一个长调用都有**。
> 补上它看起来只是顺手统一一下惯例。我准备加 12 秒。
>
> 加之前先量了一下这件事本来要多久 —— **12 秒会砍掉六成本来能成功的砍树。**

## 背景:一个刺眼的不一致

我们每个动作有 30 秒封顶。为了让封顶真能生效,代码里凡是可能长时间不返回的调用,
都套了 `Promise.race` + 超时:

```js
// src/bot.real.js:1669 —— explore 走路
await Promise.race([
  bot.pathfinder.goto(goal),
  new Promise((_, rej) => setTimeout(() => rej(new Error('75秒没走到')), 75000)),
])
```

同样的写法在 `:1637`、`:1755`、`:2570` 各有一处。唯独砍树那一行是裸的:

```js
// src/bot.real.js:1377
await bot.collectBlock.collect(block)   // 走过去 + 挖掉 + 捡起掉落物
```

而 `mineflayer-collectblock 1.6.0` 的 `lib/CollectBlock.js` 全文 **254 行,零个 `setTimeout`**
(我在解开的 npm 原包里 grep 过,不是从文档或帖子抄的)。

看到这里,结论几乎是自动的:**这是个缺口,补上它。** 我打算写 12 秒。

## 先量:这件事本来要多久

12 这个数从哪来的?没有来处 —— 它只是"感觉挺久了"。
而这个仓库有一条已经很贵的教训([13](13-magic-numbers.md)):拍脑袋定的常数,
每一个都在后面制造一次事故。

所以先量了成功的 `gather_wood` 实际耗时(口径见文末附):

| | |
|---|---|
| 样本 | 1486 次动作,其中成功 **409 次**(28%) |
| 中位 | **14.1 秒** |
| 75% 分位 | 22.2 秒 |
| 90% 分位 | 27.0 秒 |
| 最长 | 53.9 秒 |

这里的"成功"判的是**背包木头数真的涨了**,不是 `collect()` 正常返回 ——
这两件事不是一回事,原因见 [19](19-stop-is-not-stopped.md)。

**中位数比我要加的超时还长。** 也就是说,一半以上成功的砍树会被这个"保护"当场掐死。

同一批 409 个成功样本,不同封顶值能保住多少:

| 单棵封顶 | 保住的成功 |
|---|---|
| 8 秒 | 10% |
| **12 秒** | **37%** |
| 16 秒 | 56% |
| 20 秒 | 68% |
| 24 秒 | 81% |

> **加 12 秒不是"补上一个缺口",是"删掉 63% 的功能"。**

## 为什么读代码发现不了

因为**代码里的不一致是真的,而从不一致推出来的结论是错的**。

`collect()` 确实没有超时,别的调用确实有,补齐惯例确实是对的方向 ——
每一步都成立,只有那个具体的数字是错的。而超时这种东西,
**数字就是它的全部**:一个超时的模式再正确,常数错了就是净损失。

这也是为什么静态审查、代码规范、"所有 await 都要有超时"这类规则抓不到它:
它们能告诉你这里该有个超时,不能告诉你该是多少。

## 上游怎么说

按这个项目的规矩,动手前先查了社区。结论是:
**这个问题上游知道快五年了,从来没被当成"缺超时"立过案,也没有任何 PR。**

- [`mineflayer-pathfinder#222`](https://github.com/PrismarineJS/mineflayer-pathfinder/issues/222)
  ——2021-11-23 开,**至今 OPEN**。复现步骤直接用的 `collectBlock.collect()`,原话:
  > it does not throw any error, nor does it trigger any 'goal_reached', 'path_updated',
  > or 'path_reset' events … **It also does not time out**

- [`mineflayer-collectblock#34`](https://github.com/PrismarineJS/mineflayer-collectblock/issues/34)
  ——2020-11-08 由**原作者自己**开的,至今 OPEN。同一条里有人逐字问了
  "有没有一个超时函数,让它跳到下一个方块",答案是没有。

- 在 collectblock 仓库里搜 `timeout` 命中的四条(#130 / #46 / #101 / #62),
  说的全都是 pathfinder 内部 A\* 的思考超时(`Took to long to decide path to goal!`),
  **和"整个 collect() 耗时封顶"是两回事。**

而社区里真正落地过封顶值的两个项目,选的是 **90 秒**(一个同类的本地模型 MC 机器人)
和**动作级 10 秒后直接杀进程**(mindcraft)。**没有一个人用 12 秒。**

⚠️ 顺带纠正一个容易搞错的仓库地址:`TheDudeFromCI/mineflayer-collectblock` 是一个
**fork,issue 功能已关闭,最后一次推送停在 2022-04-27**。真上游是 `PrismarineJS/` 那个。

## 🔴 但是:「没有超时」这句话我也说得太满了

写到这里我回头核了一遍自己的措辞,发现 **"`collect()` 完全没有超时"是不准确的**。

`CollectBlock.js` 这个文件确实零个 `setTimeout`,但 `collect()` **通过它 await 的东西
继承了好几个真实时限**:

| 来源 | 时限 | 表现 |
|---|---|---|
| `mineflayer-pathfinder 2.4.5` 的 A\* 思考超时 | 默认 **5000ms** | `goto()` 以 `Timeout` 拒绝 |
| 同上,卡住判据 `index.js:632` | **3500ms** | 触发 `path_reset('stuck')` |
| `mineflayer` 的 `bot.dig` | 按 `digTime` 计算 | 挖不动会结束 |

真正无界的只有两处:**走路-重新规划的循环**(一直找得到新路就一直走),
和 `CollectBlock.js:50` 的 `waitForPickup`(等 `entityGone` 事件,没有任何兜底)。

所以准确的说法是:**不是"没有超时",是"没有整体封顶,而局部时限管不到整体"。**
这个区别很重要 —— 它决定了超时该加在哪一层。

## 教训

**1. 加超时之前,先量这件事本来要多久。**
   否则你会用一个正确的模式,去破坏一个本来正常的功能。这里的账是:
   中位 14.1 秒的操作,配 12 秒的封顶,等于关掉一半以上的成功。

**2. 「这里缺一道保护」和「这道保护该多严」是两个独立的判断,后者才是全部难度。**
   前者靠读代码就能得出,后者只能靠量。而只做前一半的修复,看起来和完整的修复一模一样。

**3. 缺口本身可能就是上游的结论。**
   这个库五年没加超时,不是没人注意到 —— 是[原作者自己开的 issue](https://github.com/PrismarineJS/mineflayer-collectblock/issues/34)
   还开着。一个存在很久、很显眼、却没人修的缺口,先假设它难,别假设它被忘了。

**4. 措辞要和证据一样精确。**
   我写"完全没有超时"的时候,手上的证据只支持"这个文件里没有 `setTimeout`"。
   这两句话差得远,而后一句才是我能证明的。

> **「这里没有超时」是一个观察。「这里该加 12 秒超时」是一个决定。**
> **中间隔着一次测量,而那次测量花了十分钟。**
