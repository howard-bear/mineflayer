# 死亡到底该怎么数 —— 一个错的口径,和它带塌的一串结论

> 这是整个项目里最贵的一次更正。
> **我用了一整晚的死亡统计口径,只抓到真实死亡的约 0%。**
> 而更糟的是:我拿那个口径去"证伪"了一个**准确**的信号,然后据此把准确的信号关掉了。

## 一、三个来源,只有一个是真的

同一个 34.7 分钟窗口,四种数法:

| 来源 | 这个窗口 | 终身累计 | 占真实 |
|---|---|---|---|
| **服务器玩家统计**<br>`world/stats/<uuid>.json` → `stats["minecraft:custom"]["minecraft:deaths"]` | **194** | **1125** | **100%** |
| 机器人收到的死亡广播(聊天里那条 `XiaoMai was slain by …`) | 194 | 1039 | **92%** |
| 机器人自己记的账(过滤之后) | 4 | 270 | 24% |
| **`grep` 服务端的 `logs/latest.log`** | **~1** | — | **≈0%** |

终身累计的对账也是同一个比例:**统计 1192 / 广播 1106 / 过滤后记账 329**
→ 广播占真实 **92%**,而那道过滤只放过 **24%**。

**控制台日志根本不是死亡的记录来源。** 它漏记 5~10 倍甚至更多。
真实死亡率:终身平均 **≈35 次/小时**,爆发时 **228~336 次/小时**。
而我基于 `latest.log` 报出来的是"每天几次"。**差了两个数量级。**

### 独立复核(不是转述,是重新量的)

上面那组数字来自一次具体的对账。写这篇文档之前我又独立量了一遍,结论一致:

```
plugins/Essentials/config.yml:1231   respawn-at-home: true
  官方注释:When users die, should they respawn at their first home or bed,
            instead of the spawnpoint?

world/stats/<uuid>.json
  minecraft:deaths       = 1193
  minecraft:play_time    = 2536613 刻 = 35.2 小时
  → 终身平均 33.9 次/小时
  minecraft:damage_taken = 333651

对照:同一天 logs/latest.log 里 grep 得到的死亡行 = 9 条
```

## 二、正确的量法(写成协议,别凭记忆)

统计文件在磁盘上,**服务器不会实时刷盘**。所以两次读之间必须各存一次:

```bash
mc-rcon 'save-all'; sleep 4; 读一次        # ← 第一次也要 save-all
sleep N
mc-rcon 'save-all'; sleep 4; 再读一次
```

🔴 **这里栽过一次**:第一次读的是磁盘上的旧文件,只在第二次前 `save-all`,
于是把"上次自动存盘以来的累计"错算成"N 秒内的增量",报出了"90 秒死 37 次"。
按正确协议重测(120 秒):**0 次**。那个 37 是假的。

## 三、错口径带塌的东西

机器人侧原本有一道"误报过滤",要求同时满足:
① 服务器广播过 **且** ② 血量和饱食度都回满 20 **且** ③ 30 秒内去重。

这道过滤把 **3/4 的真实死亡扔掉了**:

- **②永远不成立**。`keepInventory` 下瞬间重生、刚站起来就继续挨打,
  1.5 秒后读到的血量常是 **16.33** 而不是 20。
- **③也在吃数据**。它爆发时每 6~10 秒死一次,**30 秒的去重窗口本身就会吞掉三分之二**。

而当初把 ① 从"或"收紧成"且"的依据是:
> 「服务器 `latest.log` 里根本没有那两条广播,所以是幻影广播。」

**那个依据就是错的。** 那两条很可能是真死亡。

> **用一个漏记的日志去证伪一个准确的信号,然后据此把准确的信号关掉了。**

改法:**只认服务器广播 + 2 秒去重**。绝不要再用"满血满饱食"当判据。
改完之后三方精确对上:统计 4 / 广播 4 / 记账 4。

## 四、死亡闭环的真机制:`respawn-at-home: true`

死亡是**阵发**的,不是持续的 —— 某几分钟里每 6~10 秒死一次,然后自己停。
先后猜过两次都错了:

- ❌ "陷入死亡循环" / "跑了两个进程" —— 都被自己证伪
- ❌ "逃命反射发 `/home base` 传送回家,而家里有怪" —— 据此加了一道**只拦 `/home base`** 的护栏,
  护栏**确实按设计触发了**,**但死亡没停**

真因在**服务端插件配置**里:

```yaml
# plugins/Essentials/config.yml:1231
respawn-at-home: true
# 官方注释:When users die, should they respawn at their first home or bed,
#          instead of the spawnpoint?
```

**死 → 插件自动把它重生【在家】→ 怪就蹲在那儿 → 6 秒后又死 → …**
全程不经过任何 `/home` 命令,所以拦命令的护栏当然拦不住。

证据链:
1. 死亡地点几乎全是同一格(它家的坐标),凶手每次都是 zombie;
2. 「我死了」之后的第一条坐标连着五个都是家;
3. 三方对账证实全是真死亡(31/31/31);
4. 爆发过去后现场清空:8 格内 0 只怪、血量满、它已经走开了。

> **教训:先查服务端配置,再猜客户端行为。**

## 五、怎么打断这个闭环(不改全服设置)

问题的核心是:**刚重生时是满血 20**,而平时的逃跑判据是"血量低" ——
**那条判据在这个场景下正好不成立**,于是它满血站在怪面前等死。

```js
// 刚死过的 12 秒内,只要 8 格内有怪就无条件先跑,不看血量
if (Date.now() < justDiedUntil && nearestHostileDist <= 8) {
  log(`🏃 刚死过,${name} 还在 ${d} 格 —— 满血也先跑,别在重生点挨第二刀`)
  flee()
}
```

实测:

| 判据 | 修前 | 修后 |
|---|---|---|
| 单分钟死亡峰值 | 11~17 次 | **3 次 / 1 次** |
| 每小时死亡率 | 爆发期 228~336 | **7.4** |
| 死亡地点 | 几乎全在家那一格 | **散开了** |
| 三方对账 | — | 5/5/5 精确一致 |

## 六、可以带走的四条

1. **先确认你的度量对不对,再去解释你量到的东西。**
   一个错的口径不会让你"少知道一点",它会让你**推出方向相反的结论**,
   然后你会基于那个结论去改代码。
2. **两个来源打架时,不要默认"更官方的那个"是对的。**
   这里"服务端日志"听起来比"客户端收到的聊天广播"权威,实际正好相反。
3. **玩家统计文件(`world/stats/<uuid>.json`)才是 Minecraft 里各种计数的真相。**
   死亡、伤害、移动距离、游戏时长都在里面。读之前先 `save-all`。
4. **凡是"过滤误报"的逻辑,都要单独验证它的漏报率。**
   我们只盯着"会不会虚报",从来没人问过"会不会漏报" —— 而它漏掉了 76%。

## 附:同一晚栽的另外两次"工具在骗人"

- **`cut -c` 截断中文** → 产生非法 UTF-8 → 某些 `grep` 实现**一条都不输出**(不是报错,是静默给空结果)。
  两个等待循环因此各空转了 4 小时 56 分和 3 小时 49 分。
- **RCON 读箱子时把输出截断在 300 字符**再数槽位,只数到 2 个,于是宣布"箱子只用了 2/27,
  所以 `destination full` 这个错在骗人"。逐槽位点名 + 负对照重数:**27/27,满的**。
  **`destination full` 一直在说真话。**

- **节流过的日志不能当事件计数器**。放置闸门那条日志是"前 3 次逐条、之后每 50 次一条",
  计数器还每次重启归零。日志 766 行 → 按重置点切成 43 段、各段最大值求和 = **至少 32039 次**。
  我在这条上**连错两次**:先把行数当事件数(小了 42 倍),
  又据此宣布"数字不可用"(过度修正 —— 其实能反推出下界)。详见 [14](14-the-gate-only-guards-half.md)。
- **`gh api` 会返回缓存**。核对仓库里到底推上去了几篇文档时,`gh api` 给的是旧数据
  (报 9 篇、时间戳停在几小时前),据此得出了"后面的全没推上去"的结论 —— **是错的**。
  绕开缓存重查(`--cache 0` + `git ls-remote` + 直接拉 raw)才拿到真相:10 篇,全在。

> **查容器、查背包,一律逐槽位点名 + 负对照。
> 查远端状态,至少用两种互不相干的方式对一次。
> 截断、缓存、漏记、节流 —— 它们都不报错,只是安静地给你一个合理的错答案。**
>
### 🔴 而"没找到"这种结论,必须有正对照才成立

查"它有没有床"时,第一次的结论是**没有** —— 而那个结论**不成立**,因为我的正对照
(查一样它肯定有的东西)返回了空。也就是说:**查询本身就没生效**,
"没找到"只是因为我问错了,不是因为它没有。

事后查明原因是嵌套 heredoc 里的引号被吃掉了 —— **查询语句压根没发出去**。

换成自带负对照的写法之后才敢下结论:

```
负对照(查一个绝对不存在的 beacon) → Found no elements    ✅ 说明"查不到"长这样
正对照(查一样点名确认存在的东西)   → 返回了数据          ✅ 说明查询有效
正式查 16 色床                      → 全部 Found no elements  ← 这才可信
```

> **一个"没找到"的结论,强度完全取决于你能不能证明"如果有,你就能找到"。**
> 没有正对照的"没找到",什么都不能证明 —— 它和"我没去查"是同一个证据强度。

> 收成一句:**拿任何计数去下结论之前,先问一句 —— 这个数是原始的,还是被加工过的?**
> 加工方式就那么几种:**截断**(只给你前 N 个字符)、**漏记**(源头就没记全)、
> **节流**(记了但按频率压缩过)、**缓存**(给你的是旧的)。
> 四种都会给出一个**看起来合理**的数,而合理正是它们难被发现的原因。
