# 拍脑袋定的数字

> 这个项目里出过好几次事故,根因都不是逻辑错,而是**某个常数是猜的**。
> 更糟的是:猜错的常数**不会报错**,它只是让某段代码永远走不到、或者让某个判断永远为假。

## 一、超时预算算错了,诚实的报错就永远打不出来

合成动作里的等待是 `20000 + 12000 = 32000` 毫秒,而动作超时封顶 `ACT_CAP_MS = 30000`。

```
动作跑到 30 秒 → 被封顶掐掉 → 返回"这个动作卡了 30 秒"
动作自己那句"合成等了 32 秒还没出来,可能是……" → 永远打不出来
```

**那句诚实的报错是为了诊断写的,而它在数学上不可达。**
更糟的是掐掉之后函数后半截还在跑,还会去开合成窗口 —— 记账会花。

两条修法(都做了):
1. **按剩余预算发超时**,而不是写死一个比封顶还大的数
2. 用 `actingSince` 当 **epoch 令牌**:
   ```js
   const epoch = actingSince
   const cutAlready = () => actingSince !== epoch   // 大脑换了动作 = 我已经被掐过了
   ```
   被掐之后所有后续步骤先问一句 `cutAlready()`,是就立刻收手。

> **任何"内部等待"都必须小于"外部封顶",否则内部的错误处理是死代码。**
> 写完超时,拿计算器加一遍。

## 二、"挪一步"的尺度被拿去量"走一趟"

给合成加了一条"离工作台太远就别走了"的早退,门槛拍了 **8 格**。

部署后 **7 分钟**就抓到它把 **8.5 / 9.0 / 9.8 格** 三次一并否了 —— 那明明是几秒钟就能走到的距离。
8 这个数字是拿"站着伸手够得着"的尺度去量"走一趟",单位就错了。

重定的办法是**先量真速度**,不是再猜一个:

```
全天 5878 个位移样本
  中位数     0.86 格/秒
  75% 分位   2.42 格/秒

10 秒的走路预算 × 75% 分位 ≈ 24 格  → 取 20 格,留 CRAFT_WALK_MAX 可覆盖
```

> **门槛要和它要衡量的动作同一个量纲。**
> "够得着"是米级、"走一趟"是十米级,差一个数量级。
> 而且门槛应该从**实测分布**里推出来,不是从直觉里。

## 三、去重窗口比事件间隔还长,就会吞掉事件

死亡记账原来是 **30 秒去重**。而它爆发时**每 6~10 秒死一次**。

**30 秒的窗口本身就会吞掉三分之二的真实死亡。**
这不是过滤"误报",这是在用一个比信号周期还大的采样窗口去采样。

改成 **2 秒**之后,三方对账精确对上(详见 [10](10-counting-deaths.md))。

> **设去重/节流窗口之前,先问:我要去重的那个事件,最快能多密?**

## 四、反过来:太小的间隔会把别人饿死

决策间隔的下限原来是 **300 毫秒**。机器人于是把本地模型打满,
而**同一台机器上还有一个对话 NPC 在给真人小孩回话** —— 它的延迟从 443 ms 涨到 **10156 ms**。

把下限提到 **2500 毫秒**之后:

| | 改前 | 改后 |
|---|---|---|
| NPC 回话延迟 | 10156 ms | **3384 ms** |
| 机器人自己的决策次数 | 23 | **45** |

**慢一点反而快** —— 因为不再互相排队。

> **在共享资源上,"我尽量快"和"整体快"经常是反的。**
> 而代价往往落在**唯一有真人在等**的那条路上。

## 五、这几条的共同点

| 常数 | 猜错的后果 | 怎么定才对 |
|---|---|---|
| 内部等待 vs 外部封顶 | 错误处理成了死代码 | 算一遍,内部必须更小 |
| 距离门槛 | 把该做的事否掉了 | 从实测位移分布推 |
| 去重窗口 | 吞掉 2/3 的真实事件 | 从事件最快间隔推 |
| 决策间隔下限 | 把共享资源打满,饿死别人 | 从**别人**的延迟推 |

**四个都不报错。** 它们只是安静地让某件事不发生 ——
而"某件事不发生"在日志里长得和"没发生过"一模一样。

准备给砍树加一个 12 秒超时,加之前先量了成功的砍树本来要多久 ——

它制造的事故会和上面四个长得一模一样:不报错,只是砍树安静地少了六成。
