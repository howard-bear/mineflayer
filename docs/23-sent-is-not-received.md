# 「发出去了」不等于「收到了」

> 我跟 Owner 报告:网页发的话已经**真的送进游戏**了,测试通过。
> 那句话是错的。**它一条都没送进去,而且连着三轮测试都没暴露。**

## 那个 bug

一个手写的 RCON 客户端,数据包长度算成了**字符数**:

```python
def pkt(i, t, body):
    b = body.encode("utf-8") + b"\x00\x00"
    return struct.pack("<iii", 10 + len(body), i, t) + b
    #                          ^^^^^^^^^^^^^^ 字符数
```

正确的是字节数(`b` 里已含结尾两个 `\x00`,所以是 `8 + len(b)`)。

一个中文字符是 3 个字节。所以一条带中文的命令,声明的长度比实际短一大截,
服务端读到半截包 —— **然后把它丢掉**。

## 它为什么能骗过三轮测试

**因为它的失败没有任何信号:**

```
sendall()      成功返回
异常           没有
错误码         没有
回执           空字符串
```

而且 —— 这是最要命的一点 —— **纯英文命令完全正常**。
ASCII 字符 1 字符 = 1 字节,两种算法结果一样。

> **一个只在非 ASCII 下发生的失败,用英文测试永远测不出来。**

这台服务器上的一切都是中文的:玩家昵称、聊天内容、菜单文字。
而我随手写测试时用的是 `ascii only` 这种串。

## 我是怎么"验证通过"的

我的端到端测试是这样的:

```
发一条 → 接口返回 {"ok": true} → 去 chat.json 里查,那条在
```

**而 `chat.json` 是我自己的代码写的。**

真实的流程有两段:
```
网页 → [我的服务] → chat.json      ← 我验证的是这一段
                  → RCON → 游戏     ← 我没验证的是这一段
```

我拿「我把它记下来了」当成了「它到了」。

> **验证一条链路的时候,要检查【链路另一头】的状态,
> 而不是检查【自己这头】有没有做完动作。**

## 暴露它的三步

**① 先把静默的 catch 拆掉。**

原来那段是这么写的:

```python
try:
    _rcon("mcai ask ...")
except Exception:
    pass          # ← 这行把答案藏了两轮
```

这个仓库里本来就有一条「别再写静默 catch」的教训,我还是写了一个,
**而它当场就藏住了一个真 bug。** 改成记日志之后,第一条诊断就是有用的:

```
[diag] AI-ASK ok name=老麦        ← "我发出去了"
```

但 AI 没有回话 —— **于是矛盾变得可见了:发出去了,却没有发生任何事。**

**② 把回执记下来,和一个已知能用的路径对比。**

```
手动 mc-rcon:  §7(问老麦: 老麦 手动这条能通吗 …)   ← 服务器确实收到了
我的服务:      ''                                    ← 空的
```

**同样的命令、同一个服务器,一个有回执一个没有** —— 差别只可能在客户端。
到这一步,问题的范围从"整条链路"缩到了"我那 30 行 RCON 代码"。

**③ 造一个能给出确定答案的判据。**

`tellraw` 成功时没有输出,所以"没回执"不能区分成功和失败。
于是把它发给一个**不存在的玩家**:命令真执行会回 `No player was found`,
包坏了才是空字符串。**把一个没有输出的操作,改造成一个有输出的操作。**

然后拿修好的和修坏的并排跑:

```
                 修好的      修之前
纯英文 tellraw    ✅执行      ✅执行     ← 所以英文测试永远测不出来
含中文 tellraw    ✅执行      🔴丢了
含中文+表情       ✅执行      🔴丢了
```

**先把"没修时是错的"复现出来,再信那个修复** —— 这条仓库里已经有了,
这次它还额外证明了一件事:**问题确实是编码相关的,不是别的巧合。**

## 修完之后,真的通了

```
网页发:  老麦 网页这条能通了吗
回执:    §7(问老麦: 测试员(在网页上)问你:老麦 网页这条能通了吗 …)
10 秒后: [McAI] [村民] [村民 老麦] 哈姆,我是个村民,不搞网页测试。你问管理员吧。
```

## 教训

**1. 🔴 「我发出去了」和「对方收到了」是两件事,中间必须有一个回执。**
   没有回执的协议,要自己造一个(比如故意发一条会报错的,看它报不报)。
   **一个永远不会失败的发送函数,不是可靠,是没在看。**

**2. 验证要看链路的另一头。**
   我查的是自己写的那份 JSON —— 那只能证明我的代码跑过了,
   不能证明消息到达了。**自己的记录不是对方的收据。**

**3. 用真实数据测,不要用 `test` / `ascii only`。**
   这台服务器上没有一句话是纯英文的。
   **测试数据和生产数据的字符集不一样,等于没测。**

**4. 静默的 catch 会让你多绕两圈。**
   它不是"少一条日志",它是**把矛盾抹平了**:
   有日志时我看到「发出去了 + 什么也没发生」,立刻知道哪里不对;
   没日志时我只看到「什么也没发生」,而那和"AI 不想理你"长得一模一样。

> **写下"已验证"之前,先问:我验的是它做到了,还是我做完了?**

---

⚠️ **附:这篇里我没复核的**

- 我只验证了 `tellraw` 和 `mcai ask` 两条命令在修复后能执行。
  **没有系统地测过更长的中文命令**(RCON 单包有长度上限,超长命令是另一个话题)。
- 「一个中文字符 3 字节」对常用汉字成立,但 emoji 等增补平面字符是 4 字节。
  结论不受影响(方向一样),但如果有人拿这篇去推算具体长度,注意这一点。
- 我没有读 `mc-rcon` 那个包装脚本的实现,只把它当成"已知能用"的对照组。
  **它为什么是对的,我没有核实过** —— 我只用了它的结果。
