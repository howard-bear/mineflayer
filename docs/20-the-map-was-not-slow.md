# 地图不刷新,而地图一直在刷新

> Owner 说:「bluemap 是不是刷新很慢,我新去的一些新区域他多久才刷出来?」
> 我差点去调渲染线程 —— 而渲染根本不是瓶颈,**瓶颈在浏览器里,不在服务器上。**

## 一个立刻成立的解释

这台服务器上 BlueMap 有 **55 张地图**(主世界 + 下界 + 末地 + 49 个资源世界),
而 `core.conf` 里写着:

```
render-thread-count: 2
```

55 张图、2 条渲染线程 —— **「排不过来」这个解释一秒钟就成立了。**

更糟的是,这个仓库里已经有一条**正确的**教训在给它背书:
`render-thread-count` 调到 6 会吃掉 16 核里的 11 核,让玩家卡在「加载地形中」而 TPS 仍显示 20.0。
所以那个 2 是**故意压下来的**,是拿地图速度换玩家流畅度的一次自觉取舍。

于是故事非常顺:**我们自己把它压慢了,现在报应来了。**

## 先量

顺不等于对。量了三段:

| 环节 | 实测 |
|---|---|
| 区块存到硬盘 → BlueMap 排进队列 | **约 5 秒** |
| 排进队列 → 对应瓦片写出来 | **最快 0.7 秒** |
| 主世界 10 分钟写出的瓦片 | **1745 块**(全部地图合计约 2400) |

渲染线程确实是满的 —— `top` 里两条 `BlueMap` 线程都钉在 **99.9%**。
但满载**不等于**落后:它只说明一直有活干,不说明活在堆积。

真正该量的是**延迟**,而延迟是几秒。

> **服务器侧从「玩家走过去」到「地图画好」,是分钟级里最快的那一档 —— 受限于 5 分钟存盘一次,不是渲染。**

## 真因

```
$ curl -I https://<地图域名>/maps/world/tiles/0/x5/7/z1/1/4.prbm.gz
HTTP/1.1 200 OK
Cache-Control: public, max-age=86400
```

**86400 秒 = 24 小时。**

服务器 5 秒后就把新地图画好了,而浏览器被告知「这块地图存一天,别再问」。
于是你看到的是昨天那张,而且**刷新页面也不一定有用** —— 普通刷新仍然会命中本地缓存。

## 为什么在服务器上查不出来

因为**服务器侧每一个指标都是正常的**。

渲染在跑、队列不长、延迟是秒级、磁盘在写、CPU 满载但那是它该有的样子。
我把能量的都量了,每一项都告诉我「这里没问题」——**而它们全都说对了。**

问题不在我的观测范围里:**瓶颈在用户的浏览器里,而我所有的探针都在服务器上。**

> **「它慢」这句话没有说是哪一层慢。而我默认了是我能看见的那一层。**

## 修法

只给地图数据这条路径压短缓存,静态资源(js/css)不动:

```nginx
location ~ ^/maps/ {
    proxy_pass http://127.0.0.1:<BlueMap 的本机端口>;
    ...
    proxy_hide_header Cache-Control;
    add_header Cache-Control "public, max-age=60" always;
}
```

验过边界:`/maps/` 下的瓦片变成 `max-age=60`,
`/assets/index-*.js` 仍然是 `max-age=86400` —— **没有误伤。**

60 秒而不是 0:地图本来就不是秒级更新的东西,而 0 会让每次平移都重新下载全部瓦片。

## 教训

**1. 「慢」是一个没有主语的报告。**
   先问「哪一层慢」,再问「慢多少」。这次一共三层:存盘 5 分钟、渲染 5 秒、浏览器 24 小时。
   我一开始只盯着中间那层 —— 而它恰好是三层里最快的。

**2. CPU 100% 不是瓶颈的证据。**
   它只说明有活干。**要证明堆积,得量延迟,不能量占用率。**
   这两个数看起来都像「忙」,但一个是产能,一个是欠债。

**3. 🔴 一条正确的旧教训,会变成下一次误诊的证据。**
   「`render-thread-count` 不能调大」是对的,而且是花过代价才学到的。
   正因为它是对的,它让「渲染慢」这个错误假设显得有依据 ——
   **我不是凭空猜的,我是拿着一条真教训猜的,所以我更不容易怀疑它。**
   仓库里的教训越多,这种事越容易发生。

**4. 观测点决定了结论的上限。**
   所有探针都在服务器上,那么无论量多少项,结论都只能是「服务器侧的某个部件」。
   **要发现不在服务器上的原因,必须往外走一步 —— 这次是 `curl -I` 一下自己的网站。**

> **别问「它为什么慢」,先问「我是在哪一头看的」。**

---

⚠️ **附:这篇里我没复核的**

- 「0.7 秒」只抓到**一次**清楚的配对(区域排队 → 该区域瓦片写出)。
  其余样本对不上,多半是因为 **BlueMap 只在瓦片内容真的变了时才写文件** ——
  区块存盘并不等于画面有变化,所以「没写出来」不能当成「没画完」。
  **这个判据的分母不干净**,所以 0.7 秒只能当"能有多快"的下界,不能当平均值。
- 改完之后我没有蹲在浏览器前面验证"现在多久能看到新区域"。
  我验的是**响应头变了、且静态资源没被误伤**;端到端的观感由 Owner 确认。
- 55 张图共用 2 条线程这件事**依然是真的**。这篇不是说它不要紧,
  是说它**不是这次那个现象的原因**。资源世界的地图确实会比主世界慢,那是另一笔账。

版本:`BlueMap 5.16`(Spigot)、`Paper 1.21.4`、`nginx` 反代。
`core.conf` / `plugin.conf` / `bukkit.yml` 的取值都是在服务器上直接读的。
