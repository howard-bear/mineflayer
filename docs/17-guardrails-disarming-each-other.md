# 护栏互相拆台

> 为了保命加了一道闸。那道闸**正确地**挡住了一批动作。
> 而挡住这件事本身,把**另一条保命规则**解除了武装 —— 那条规则防的是头号死因。
>
> 两边都没有 bug。是**记账**把它们连在了一起。

## 机制

新加的规则是"天黑了就去睡觉"。睡着大约 9 分钟,期间有一道闸:**正在睡觉时拒绝别的动作**。

而优先级更高的几条硬规则(做装备 / 吃饭 / 打猎)照样会抢到那个 `forced` 槽位,
然后被这道闸拒掉。被拒掉的结果,和"这个动作真的失败了"记在**同一个计数器**上:

```
睡着 → 强制吃饭规则抢到槽位 → 被"我正在睡觉"拒绝 → failCount('eat')++
eat 的节流是 3 秒 → 约 9 秒 就把 failCount('eat') 顶到 3
                    ↓
强制吃饭规则自己的前置条件是  failCount('eat') < 3
                    ↓
        ❌ 整条规则停摆,而衰减要 3 分钟
```

**而饿死是这个机器人的头号死因**,反射层里又没有吃饭分支。

所以完整的因果是:**一道为了保命而加的闸,在 9 秒之内把防止头号死因的那条规则关掉了 3 分钟。**

## 为什么这类问题特别难发现

- **两个部件各自都对**。睡觉时拒绝别的动作是对的;失败三次就冷却也是对的。
- **日志上看不出异常**。你会看到"强制吃饭"规则安静下来,而它本来就不是每轮都触发。
- **它只在两个条件同时成立时出现**,而其中一个(睡觉)是刚加的。
- 最要命的是:**新加的那道闸越"正确",拒绝得越多,拆台就越彻底。**

## 根因:两种"失败"被混在一起

```
动作失败了       ← 它试了,没做成。该记,该冷却。
被规则挡住了     ← 它根本没试。不该记,更不该因此冷却。
```

`failCount` 这个机制的本意是"这个动作最近老是做不成,先别选它了"。
而"被闸挡住"根本不是"做不成",它是"现在轮不到"。

修法是给闸门拒绝一个**单一来源**的标记,让**生成**和**识别**用同一份定义:

```js
const GATE_TAG = '[规则挡住]'
function gateReject (why)  { return `失败:${GATE_TAG}${why}` }
function isGateReject (r)  { return typeof r === 'string' && r.indexOf(GATE_TAG) >= 0 }
```

然后记账处跳过 `isGateReject` 的结果。

> 注意这又是[同一个函数原则](01-inventory-full-blocks-everything.md)的一次应用:
> 如果"怎么写这句拒绝"和"怎么认出这句拒绝"是两份代码,**它们一定会漂**。

## 同一批里的另外两条,都是"安全机制的二阶效应"

### ① 看起来像菜单的东西,其实是执行闸

角色的动作白名单(一个 JSON 配置)看起来像"给模型看的菜单"。
所以加新功能时很自然地想:*"不改它只是模型选不到,硬规则还能跑。"*

**错的。** 它是 `executeAction` 的第一句:

```js
// 菜单那道是"不提供",这道是"提供了也不许做" ——
// 而且硬规则(forced)是绕过菜单直接塞动作的,只靠菜单挡不住。
if (a && a.action && !ROLE.actions.includes(a.action)) return gateReject(...)
```

**硬规则绕过了菜单,但绕不过这道闸。** 不改白名单的话,整个新模块会是**死码** ——
规则打日志、打时间戳、塞 `forced`,然后当场被拒,真正的函数一行不跑,
**而且每次还往经验库写一条假原因**。

> **搞清楚一个配置是"建议"还是"强制"。** 两者长得一样,后果差一个数量级。

### ② "永不处理"清单需要有上限

为了不让做床的羊毛被存进箱子,把"所有羊毛"加进了 `STORE_NEVER`(永不入库)。

审查算出来的问题:**野外的羊有 6 种颜色**,用不上的那几色会**永久占格**。
而"背包全满却没有可以扔的杂物"这条日志**已经命中 58 次** —— 背包本来就是稀缺资源。

改成"每色留 3 个,多的照常入库"。

> **往任何"永不删除 / 永不清理 / 永不过期"的清单里加东西之前,先问一句:
> 它会不会无限累积?** 只有**天然有上限**的东西才配进 NEVER。

### ③ 一条话多的新规则,会安静地吃掉历史

新规则第一版**没有加时间戳节流**,真睡着之后每 2.5 秒记一条 ——
一夜约 **220 条**。而经验库是 `MAX = 500` 的 FIFO(`records.slice(-MAX)`)。

**一夜挤掉 44% 的历史。** 而且我查了一下:`memory.json` 现在**正好卡在 500** ——
淘汰机制一直在生效,任何一个话多的新写入都在实时挤掉旧记录。

> **往一个有上限的 FIFO 里写东西,写入频率就是别人的删除频率。**

## 收束

这四条的共同形状是一样的:

| | 加的东西 | 二阶效应 |
|---|---|---|
| 1 | 睡觉时拒绝别的动作 | 把防饿死的规则关掉 3 分钟 |
| 2 | 角色动作白名单 | 不改它,新模块整个是死码 |
| 3 | 羊毛永不入库 | 6 色羊毛永久占格,而格子已经不够 |
| 4 | 睡觉状态记日志 | 一夜挤掉 44% 的经验历史 |

**没有一条是"写错了"。** 四条都正确地做了它们被要求做的事。
问题出在它们和**已有机制的接缝**上 —— 而接缝是没有主人的。

> 加一个新机制的时候,除了问"它对不对",还要问:
> **它会消耗谁的预算?它的输出会被谁当成输入?它拒绝的东西,会被谁记在账上?**
