# 我只修了被报告的那一个

> 孩子反馈「资源世界的按钮不见了」。我找到真因、修好、验证通过、汇报完成。
> **然后 Owner 说:你把它放到了「世界传送」的位置上,而那个按钮也不见了。**

## 现场

一次后台的「商店物价 · 保存」,会跑 `gen_shop.py`,而它**整份重写**两样东西:

- `gui_menus/main.yml`(指南针主菜单)
- `DeluxeMenus/config.yml` 里的 `gui_menus:` 注册块

主菜单上的「资源世界」是几周前**手工加进 `main.yml`** 的,生成器从来不知道它存在。
所以那次保存把它抹了 —— 连同它的菜单注册一起。

```
/var/log/mc-shop-regen.log
[2026-09-17 23:52:04] shop-regen: regenerated + dm/ess reload OK
[2026-09-17 23:52:24] shop-regen: regenerated + dm/ess reload OK
菜单生成完成:main + jobs + 12 职业详情 + shop_main + 6 分类 + 66 件卖价
```

> **触发它的动作(改商店物价)和坏掉的东西(资源世界入口),看起来毫无关系。**
> 所以第一反应绝不会是「我刚才点了保存」。

## 我修完了,而且修错了一半

我把「资源世界」写进生成器、跑一遍、`dm reload`、确认按钮回来了、汇报完成。

**我把它放在了 13 号格 —— 因为那一格是空的。**

那一格之所以是空的,是因为「世界传送」也被同一次重写抹掉了。
我拿一个故障去填了另一个故障留下的坑,**还把它盖住了**。

历史布局是这样的(从 8 月的备份里翻出来):

```
13 格  世界传送 Travel ワープ     ← 被抹了,我没发现
20 格  资源世界 Mining 資源       ← 被抹了,有人报告了
```

## 为什么我没发现

因为**我按报告去修,而报告里只有一个**。

> **报告的人只会报告他自己会用的那一个。**
> 「没有人报告」不是「没有坏」,只是**那个功能的用户今晚没上线**、
> 或者上线了但没点到、或者点了但以为是自己记错了。

孩子会报告资源世界,是因为他们每天都去挖矿。
没人报告世界传送,是因为 Strix 本来就连不上,大家早就不点它了 ——
**一个坏掉很久的功能,会掩护一个刚坏掉的功能。**

## 该用的排查方法

不要从「报告了什么」出发,要从「应该有什么」出发。这次用的两个判据都很便宜:

**① 孤儿扫描 —— 拿文件和注册表对账。**

```bash
for f in gui_menus/*.yml; do
  b=$(basename "$f" .yml)
  grep -qE "^  $b:" config.yml || echo "🔴 $b 有文件但没注册"
done
```

跑出来三个:

```
🔴 strix             1515 字节,改于 2026-08-29,但没注册   ← 真的被抹了
   advanced_menu     插件自带示例,本来就不注册
   requirements_menu 插件自带示例,本来就不注册
```

**这个判据的好处是它不需要有人报告。** 它问的是「有没有东西对不上」,而不是「谁喊疼」。
(反方向也要跑一遍:注册了但文件不在的。这次是空的。)

**② `dm reload` 的菜单计数,是个免费的整数指纹。**

```
修之前          23 menus loaded
补回资源世界     24 menus loaded
补回世界传送     25 menus loaded
```

一个整数,每补一样就 +1。**它把「我以为我修好了」变成「我数得出来我修好了几个」。**
这种能直接读到的计数,比任何"看起来正常"都硬 —— 而且它当场就证明了
那两个菜单在此之前**根本没被加载过**,不是"加载了但打不开"。

## 修法:写进生成器,不要手工改

```python
item(o,'strix',13,'ENDER_PEARL',tri('&b&l世界传送','Travel','ワープ'),['[openguimenu] strix'], ...)
item(o,'resworld',20,'DIAMOND_ORE',tri('&b&l资源世界','Mining','資源'),['[openguimenu] resworld'], ...)
```

注册块同理。两处都补,少一处就是下一次事故。

顺带做了件对孩子更友好的事:Strix 当时正因为上游故障进不去,
于是给它加了个**维护开关**,打开时按钮变灰、点它只弹一句说明,
不再让孩子点进去撞三次死路。开关是一行 `STRIX_MAINTENANCE = True`,
上游修好改成 `False` 重跑即可 —— **让"临时状态"有个明确的开关,比直接删掉它好。**

## 教训

**1. 🔴 修完之后,要问「还有什么和它一起坏的」,而不是「报告的那个好了吗」。**
   同一个原因造成的故障是**一批**,而报告是**一个**。
   按报告收工,等于把同一次事故拆成好几次来发现。

**2. 没有人报告 ≠ 没有坏。**
   报告量取决于「有多少人用它」,不取决于「它坏得多严重」。
   **一个平时就没人用的功能,坏了几乎不会有人喊** —— 而它往往还在别人的默认布局里占着位置。

**3. 用对账代替听报告。**
   「有文件没注册」「注册了没文件」「数量对不对」这类判据,
   便宜、不依赖人、而且能在事故**发生前**跑。

**4. 一个坏掉很久的东西,会掩护一个刚坏掉的东西。**
   这是 [19](19-stop-is-not-stopped.md) 里「两个修复互相掩护」的另一种形状:
   **那里是修复掩护 bug,这里是旧 bug 掩护新 bug。**
   共同点都是:现场看起来没有异常。

> **别问"报告的那个修好了吗",问"这次事故一共打翻了几个"。**
