# 一份代码,两个身份

> Owner 在游戏里看到:
> ```
> Bingolds  xiaomai的领地能不能取消掉一块
> MaiNiang  这个我不清楚,你问问管理员      ← 它以为在说它
> XiaoMai   这个我不清楚,你问问管理员
> ```
> 他问的是「怎么 mainiang 也回复了」。
> **而真正的问题不是它多说了一句话。**

## 一行

```js
const NAME_RE = /小麦|xiaomai/i          // bot.real.js:186
const mentioned = NAME_RE.test(message)  // :7215
```

两个 AI 玩家跑的是**同一份代码**,只是用不同的账号登录:

```
mcbot.service    XiaoMai    EnvironmentFile=/etc/mcbot.env
mcwife.service   MaiNiang   EnvironmentFile=/etc/mcwife.env    ← 同一个 bot.js
```

登录名是按实例来的(`process.env.MC_NAME || ROLE.login`),
**但"有没有人在叫我"这个判据是写死的。** 于是第二个实例拿着第一个实例的名字在认领消息。

## 为什么这不是"多说一句话"的问题

`mentioned` 同时把着四道门:

```
:7215  回话
:7231  RE_FOLLOW && mentioned   →「小麦 跟我来」
:7237  RE_WHERE  && mentioned   →「小麦 你在哪」
:7242  RE_GOAL   && mentioned   →「小麦 进度呢」
```

也就是说:**任何孩子说一句「小麦 跟我来」,麦娘也会跟他走。**

而代码里就在那道门旁边写着(原文):

> 🔴 必须【提到名字】才算指令。两个理由:
> ① Owner 的规格;② 更要紧的 —— 原来这条【不要求名字】,于是任何孩子在公屏说一句"跟我来"
>    就能把机器人牵走。那不只是吵不吵,是【谁能指挥它】的问题。

**护栏写对了,身份判据写死了,于是护栏对第二个实例整个失效。**
加护栏的人和埋雷的人是同一个,只隔了几百行。

## 为什么它能活这么久

三个条件要同时满足才看得见:

1. **两个实例同时在线** —— 麦娘是当天才上线的
2. **有人在公屏点名** —— 而 Owner 的规格是"不被点名就不说话",所以这种消息本来就少
3. **有人正好在看** —— 这次是 Owner 自己看见的

更根本的是**它的失效方式**:

> **不是"报错",不是"少做了一件事",是"多做了一件事"。**
> 没有异常、没有告警、没有一行日志说"我不该回这句"。
> 在日志里,麦娘那句回话和一次正常回话**长得一模一样**。

## 排查方法

### ① 找"本该由身份推导、却写成字面量"的东西

一份代码跑 N 个实例时,任何等于**实例 #1** 的字面量都是雷:

```bash
# 名字
grep -n "小麦\|xiaomai" bot.real.js
# 路径(同类:第二个进程会覆盖第一个的存档)
grep -nE "'/[a-z/]*\.(json|db|log)'" bot.real.js
# 端口、账号、ID
grep -nE ":[0-9]{4,5}'|process\.env\.[A-Z_]+ *\|\| *'" bot.real.js
```

判据不是"这个常量对不对",是:**换一个实例来跑,它还对吗?**

平级会话在同一天踩到了这一类的第二个:**存盘文件路径写死** ——
麦娘一上线,第一件事就是拿自己的进度覆盖小麦的 `house.json` / `land.json`,
而那两样是花了一整天做出来、还在服务器侧逐格复核过的。

> **私有的按实例隔开,共有的显式共享。**
> 而且:**第一个实例不设隔离变量** —— 这样它现有的存档零迁移,不用动。

### ② 让每个实例在启动时把"我是谁、我认什么"说出来

这是修复的一部分,不是装饰:

```
👤 我是【小麦】(XiaoMai,角色 son)
   有人喊这些名字我才当是在叫我:XiaoMai / 小麦(别人的名字一概不理)
👤 我是【麦娘】(MaiNiang,角色 wife)
   有人喊这些名字我才当是在叫我:MaiNiang / 麦娘(别人的名字一概不理)
```

> **这个 bug 能活到现在,是因为从来没有一行日志说过它认什么名字。**
> 只要这行早存在,任何人扫一眼日志就会发现两个进程认的是同一个名字。

**把"不变量"打印出来**,比事后去推它有没有被违反便宜得多。

### ③ 验证修复时,分清「改了」「部署了」「正在跑的就是它」

```bash
stat -c %y bot.real.js                              # 代码改于 01:45:06
systemctl show mcbot  -p ActiveEnterTimestamp       # 进程起于 01:45:17
systemctl show mcwife -p ActiveEnterTimestamp       # 进程起于 01:50:23
```

进程晚于代码 = 跑的是新版。但最硬的证据是**运行中的进程自己把修好的那件事打出来** ——
上面那两行启动日志就是。它同时证明了三件事:代码改对了、部署到位了、而且**两个实例确实各认各的名字**。

## 教训

**1. 🔴 一份代码跑多个实例时,任何写死的"自身标识"都是炸弹。**
   名字、路径、端口、账号。它对第一个实例永远是对的 ——
   **所以你测第一个实例,永远测不出来。**

**2. 失效方式是"多做了一件事"的 bug,最难被发现。**
   少做了会有人喊,报错了有日志,而"多做了一件事"在日志里和正常行为长得一样。
   这类 bug 要靠**不变量**发现,不能靠观察。

**3. 把不变量打印出来,当成功能的一部分。**
   「我认这些名字」这一行不是日志噪音,它是**检测器**。
   代价是一行,收益是"任何人扫一眼就能发现两个实例撞身份"。

**4. 一个护栏可能在几百行之外被自己废掉。**
   「必须点名才算指令」这条写得很清楚、理由也写对了 ——
   然后 186 行那个写死的常量把它对第二个实例整个关掉了。
   **护栏的强度 = 它依赖的那个判据的强度。**

> **加实例之前先问:这份代码里有多少东西,是"第一个我"的?**
